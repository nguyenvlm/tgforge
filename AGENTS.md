# tgforge — agent guide

Agent-facing architecture + invariants for working in this repo. `CLAUDE.md` symlinks here. User-facing usage lives in `README.md`; this file is the "why" and the rules a change must not break.

## Dev basics

- Branches: `main` (default) + `dev`, both long-lived and protected (PR-only). Land via a feature branch → PR into `dev`; `dev` → `main` promotes.
- Tooling: uv-managed venv (Python 3.12, `uv pip install -e ".[dev]"`); ruff only (`ruff format` + `ruff check --fix`), format only files you changed.
- Tests run hermetically through the repo venv (`uv pip install -e ".[dev]"`, then `env -u VIRTUAL_ENV .venv/bin/python -m pytest`) — MockBot under the real `TelegramAdapter` via `tgforge.testing.TestClient`; the Slack tests run the real `SlackAdapter` over a fake Web API client (`tests/slack_fakes.py`); no network or token.
- Design conventions: few files (framework core in `base/kernel.py`, satellite one-concept modules are the exception); a name says what it does; repo text stays generic — neutral example names (`mybot`), no personal identifiers, no live bot names.

## Platforms and the adapter boundary (`base/telegram.py`, `base/slack.py`)

- One `Kernel` holds one `Transport` per configured platform (composition); each `Transport` holds one adapter, one pacer and one flood deadline. Every platform call, update conversion and platform rule lives in its adapter; the kernel's neutral parts, `app.py`, `ui.py` and every plugin import neither `aiogram` nor `slack_sdk`, and only `base/telegram.py` imports `telegramify_markdown` (the Rich HTML render `rich_html` and the page renders live there) (`tests/test_import_boundary.py`); none holds a platform check. The adapter calls and attributes are listed at the top of the kernel's neutral types section.
- The adapter renders: standard Markdown (`render` → rich, or None when it is over one message in one of its forms, plus plain), `ui.Pages` (`render_pages`; a card's frame renders the `Pages` cut to page 1), `ui.Keyboard`. It also supplies the sizes the neutral splitters pack against: `measure` (a Markdown body's size in its largest form, for `ui.md_chunks` and its lazy form `ui.md_pieces`, which take the longest prefix that fits: the window-long prefix when it fits, else found by bisection over the cuts; `Transport.send_rich` cuts one piece ahead of its sends and the search lets the event loop run every few milliseconds. A cut falls at a newline (before an unindented line when that fills half a message), else inside the line at whitespace outside inline formatting (a code span closes on the next backtick run of its exact length, a backslash before it included; the scan stays linear in the line), else at whitespace (each only when the piece fills half a message, so no piece holds only a block marker), else at any character; a code block cut across pieces (fences indented in a list or quoted included) is closed and reopened with its fence line, never cut right after its opening line; a table cut across pieces starts each later piece with its header and delimiter rows (its first two lines, inside a quote or list item too, with their prefix), never cut right after them, and a row too long for a message with them is cut between words and continues as a row (`| `) under them; a list continuation opening a piece loses its indent (counted in columns, a tab to the next multiple of 4; a tab past the removed columns, as in code, stays a tab) so it never reads as an indented code block; a line cut midway continues with its block marker escaped; a cut that does not shorten the text fails loud) and `page_size` (one page's rendered size, for `ui.expandable_pages`); a piece spans at most the adapter's `max_message` characters (`MAX_MSG`, 4,096) and fits one message in every form: Telegram measures a body as the larger of its plain length and its Rich Message size (32 KB, 500 blocks, scaled to `MAX_MSG`; past it when the Rich HTML breaks the 16-level depth or 20-column limit; the send reuses its piece's measure), and a page on its plain length (its Rich page always fits then); and its `command_prefix` (`/`, Slack `/tgf `), which the help text quotes ("Tap" a one-token command, "Type" one after a slash command). A plugin reads its window's adapter through the public `Topic.adapter`, never the private transport. It lists the forms to try for one message (`bodies`), each one message: Telegram sends every message as a Rich Message (`sendRichMessage`, edits through `editMessageText`'s `rich_message`) — Markdown as Rich HTML (`$…$` math as `<tg-math>`, `<sub>`/`<sup>` as sub/superscripts, tables as tables, tables past 20 columns split; one walk fits the 16-level depth limit: a list or quote nests only while the deepest block inside it still fits, else it is flattened, and an inline element (or display math inside inline formatting) past the limit is written as its text alone, an open footnote definition counted, so every word stays; a `$` span opening on a digit whose closing `$` follows punctuation or a space and runs into a letter, `\` or `{` is a price before a symbol, so that `$` stays text; `rich_fits` checks bytes, blocks (an image counts as one), media (`rich_media`: 50, each Mermaid block counted as its photo, so the measure splits a piece past 50 diagrams), depth and columns), then, when Telegram refuses a message with drawn diagrams, Rich with those diagrams as code, then plain text as escaped Rich HTML, then plain text; Slack has one form. Before an essential Markdown send or edit takes the issue order, the transport has the adapter draw the rich body's diagrams (`draw_diagrams`): Telegram draws each Mermaid code block as a photo in its place (`<img src="tg://photo?id=diagramN"/>`, its PNG uploaded in the message's `media`); a diagram that does not draw stays code and raises a fallback notice naming why; the later forms, a live message (recorded synchronously) and Slack (whose image block takes no inline upload) keep the code. The renderer (`base/mermaid.py`, Playwright a core dependency) runs the mermaid.js bundle in Playwright's headless Chromium, both fetched into the bot home (`diagram_files`: `<home>/mermaid/`): the package holds only the pinned version, URL and sha256 (`MERMAID_VERSION`, `MERMAID_URL`, `MERMAID_SHA256`); `fetch_files` fetches whichever is missing (setup: `tgforge install` and `tgforge fetch-mermaid`; the bot: the adapter's `prepare` at startup and rejoin, in a child process, `python -m tgforge.base.mermaid`, killed when the renderer closes; `tgforge.testing`'s adapters fetch nothing); a bundle whose sha256 differs is deleted and never loaded, and is checked again before each browser start; a diagram that finds a file missing goes out as code with the fetch's cause in its notice and starts a fetch at most once per `IDLE_CLOSE`; one page, diagrams drawn one at a time, opened on the first and closed after `IDLE_CLOSE` (5 min) without one; a timeout (`DRAW_TIMEOUT`) or a browser failure closes it, a source Mermaid refuses keeps it, an idle close skips when a diagram drew while it waited; the page fetches no URL; each PNG is padded to Telegram's side ratio and shrunk to its width-plus-height limit. An edit is one message in every form too, and an edit to the text a message already shows changes nothing. A live message is one message in every form: its plain body and its Markdown are checked when recorded (`show_frame` / `land_frame` / `show_bottom_frame` raise when either is over one message; `Topic.fits_one_message` is the check: every caller recording Markdown cuts its content to it through `ui.most_that_fits` — the `!` output (`ui.shell_md`), the shell panel, the Files view and the background-jobs panel; a card's `Pages` fit by construction). A refused Rich Message is logged at WARNING with its error and size (a rendering defect to fix). Button-only edits stay `editMessageReplyMarkup`; photo and file captions stay plain (the rich methods carry no caption). It sorts each call's error into `Flood(seconds)`, `Transient`, `NotModified`, `NotFound` or `Refused` (`classify`); the walk through the forms (an essential call walks them under one hold of the issue order; a frame takes a fresh spare slot per form), pacing and flood waits stay in `Transport`.
- A window key is a string. Telegram: the forum thread id in decimal, General `"0"`. Slack: `slack:<channel id>`, General the control channel's key. The kernel picks a key's transport by the adapter's `key_prefix` (the longest prefix leaving a bare id); a key no configured platform owns is kept in state and not revived. Message ids stay native (Telegram `int`, Slack `ts` string) and `<` orders them within a window. Each platform's General has its own menu stack and pending text prompt, and its own owner (`owner_for(window)`).
- Inbound events are neutral: an adapter turns a message into an `Inbound` (window, message id, user id, raw text, mention flag, replied text (a Rich Message's from its blocks) / author / user id / attachments, quote (sent to Claude even when the replied text is empty), forward source, album id, attachments with a download handle, `mentioned_user_ids` (Telegram tap-mentions, Slack `<@U…>`, the bot left out), `in_thread`, `echo`) and a button tap into a `Tap`. `Context.message` is the `Inbound`; auth is `auth(kernel, event) -> bool` on each `Inbound` / `Tap` (`OwnerOnly` checks the event's platform owner); `/init` binds the platform it is typed on. `App.start` installs the SIGTERM/SIGINT handlers before startup, so a stop during startup still drains; once startup and every plugin's `on_startup` are done, it freezes the heap (`gc.freeze`) before the first update, so the long-lived startup objects are never scanned by a later collection, and registers a `gc.callbacks` hook that logs a WARNING (duration, objects scanned, objects frozen) for a full collection over `FULL_COLLECTION_WARN` (100 ms), removed when it stops. A platform that fails to connect at startup is logged and retried in the background with the source backoff (`app.py` `_serve`), then `Kernel.rejoin` revives its windows; when no platform connects the process exits non-zero (the service manager restarts it). A platform's event loop that ends is restarted after a backoff that doubles up to `SOURCE_BACKOFF_MAX`; only SIGTERM/SIGINT ends `App.start`, which drains once and then closes each adapter (`close`: Telegram's bot session, kept open through the drain). Window names are deduplicated per platform.
- Slack threads: the channel's main flow is the window's one timeline (every ordering rule below applies to it). The bot posts in a thread only for `Pages` (a finished turn's tool-call pages under its summary). A user's thread reply reaches the window as an `Inbound` whose replied text is the thread parent's text (none, with a warning, when the parent can't be read), and is never reported to `note_message`, so it never moves a bottom frame. An upload the platform takes without reporting its message id (a Slack file with no `shares` yet) marks the window's bottom frames buried (`Transport._upload`).
- Slack commands: one slash command, `/tgf`; `/tgf <text>` becomes the typed command `/<text>` (mentioned, so it also runs in General and in a raw-input window), echoed into the window (`› /<text>`) before it routes through the same slash router; a bare `/tgf` is `/`, the menu. A message typed with a space before the slash is a plain, unmentioned message: the kernel's strip makes it a slash, so it runs as a command in a window, is ignored in General and is input in a raw-input window. Every Socket Mode envelope is acknowledged before its handler runs, each handler in its own task.

## Frame-skip output (`base/kernel.py` `Transport`)

A kernel invariant every plugin follows, per platform: on a rate limit the bot stops calling that platform and keeps working locally (like a game capped at the GPU's frame rate).

- Live messages — anything updated over time (the Claude live card, the background-jobs panel, the Files view, the Shell panel, the `!` output, the mirror spinner) — go through `show_frame` / `show_bottom_frame`: the call only records the newest wanted content and returns at once (no future). One frame task pushes each recorded content when a pacer slot is spare (no essential call pending) and no flood-wait runs; content replaced before it was pushed is skipped, never sent; content equal to what landed makes no call. A finalizing edit goes through `land_frame`: it is pushed first, keeps that priority through flood-waits until it lands, and its future says whether the platform accepted it (a push that raises resolves it as not landed, so its caller goes on to its fallback). A loop reading local input records at most one frame per interval (the `!` pump: one per `EDIT_INTERVAL`, plus a timer that shows output held back by the interval when it ends), never one per line. Closing a window drops its pending frames.
- Topic titles: `show_title` (via `refresh_title()` / `rename_topic`) is the same mechanism plus at least `TITLE_MIN_INTERVAL` (5 s) between renames of one topic, since each rename posts a "topic renamed" service message; a burst gives one rename to the last name, an unchanged name makes no call. An explicit `/rename` passes `immediate` (no spacing).
- New messages and deletes (`_call`: `send`, `send_rich`, `send_md`, `delete`, one-off edits) are never skipped and go out in issue order; within a window a call takes its place in the window's send order when it starts (`Transport._window_turn`, re-entrant within a task), before anything it waits on (a diagram drawing), so a later call of that window never lands first while other windows go on. They are issued by the task that owns the sequence, never by a loop that reads local input (the CLI reader, the mirror loop, a shell's output pump): such a loop records frames or queues send steps.
- Flood-wait: on `retry_after` no call is made until the deadline (`flood_until`); every call (essential or frame push) waits for it, takes its pacer slot, and re-checks the deadline before the attempt (`_clear_to_call`: a flood recorded during the slot wait sends the slot back and starts over). An essential call waits the full `retry_after` and retries until it lands — never early. Frames keep collecting their newest content meanwhile.
- Other errors (`_attempt`): a `Transient` error (a network error or a 5xx) is retried up to `TRANSIENT_RETRIES` (3) times, 1, 2 and 4 s apart, each retry clearing the flood deadline and taking its pacer slot like the first try (`_clear_to_call` in the caller's mode), with a WARNING per retry, then given up with a WARNING; a 4xx gets one try. A failed bottom-frame move or re-send (an unconfirmed delete, a refused stub, a refused send) is retried up to `BOTTOM_RESEND_ATTEMPTS` (3) times, then waits for the next content or a newer message in its thread.
- Bottom frames (`show_bottom_frame`, with an optional keyboard): the background-jobs panel and the Files view. Every new message in the thread re-sends them below it, except one sent with `buries_bottom=False` — `Topic.send_temporary`, a notice deleted after its lifetime. A buried copy moves as one paired step: the frame task takes a spare slot and, only if a second one is free at the same moment (`take_spare_now`; `PACE_BURST` is 3), issues the old copy's delete and the new copy's send back to back; otherwise it hands the slot back and picks again after the pacer's refill time (`spare_delay`) or as soon as a new frame is recorded, so a must-land frame recorded meanwhile goes first. The send's slot, held across the delete, is re-checked against the flood deadline before the send or stub goes out (`_recheck_flood`), so no call lands inside a flood window. The send reads the frame's newest content right before it goes out. A thread never shows two copies, and the gap without one is one call (more when the platform refuses a body and the next one takes another slot; with a burst under 2, one slot). Only a landed delete or "message to delete not found" frees the old copy: a flood-waited delete retries the move, a delete whose network retries ran out may have missed and counts as a failed move (the old copy stays), and a refused delete ("message can't be deleted") edits the old copy to a `·` stub with no keyboard, stops tracking it, then sends the new copy (a refused stub keeps the old copy as the one copy and counts as a failed move). Once the old copy is gone a flood-waited or failed send retries as a plain re-send.
- A button-tap answer (`answer_tap`) takes no pacer slot (it posts no message) but still waits out a flood-wait.
- Each frame push logs one INFO line: `frame push <msg id | bottom key | title thread> [thread N]: Xs after first recorded (slot wait Ys, call Zs, R replaced, P still pending)`. A sluggish live message (a stuttering Files view) reads off it: a long slot wait is the pacer, `R replaced` counts the versions never shown, and the neighbouring lines show which other frames took the slots.
- No plugin keeps its own pacing, retry, skip, or no-op check: those live here only.

## Bot notices (`base/kernel.py` `Notice`)

- One neutral type, `Notice`: kind (`fallback` — a message went out in a lesser form; `not delivered` — no form could send or edit it, or it was cut to fit `MAX_MSG`; `exception` — caught at a bot-level boundary), window, what it hit, the form tried → the form used, the error's type and text, the payload size, a count. Each is logged at WARNING, then routed by `Kernel.notice`.
- Raised at the boundaries every path shares: the transport's form loops (`_call_bodies`: fallback and not delivered; `_attempt_bodies`: fallback only, since a frame's owner handles a frame not landing), the cut (`Transport._capped`), the frame push, the Claude send-step runner (a failed step, a step stalled past `SEND_STEP_STALL`), the reader, the heartbeat, the mirror loop, the platform loop (`app.py` `_serve`, Slack's event dispatch through the adapter's `on_notice`), the kernel's own tasks (startup, revive, restart notice, shutdown, window close), the handler dispatch (`handle_message` / `handle_tap`), the Claude plugin's helper installs at startup (in General, through the plugin's `notice`, `Kernel.notice_in_general`) and a finalized turn's `[[attach]]` file that fails (not delivered). The adapter names a form (`form_name`) and sizes a payload (`payload_size`).
- Routing: `Topic.on_notice` shows the notice in its window as a message (`⚠️ bot notice — …`, from its own task, sent with `buries_bottom=False` so it moves no bottom frame); a repeat (same kind, what and error) before the window's next inbound message counts up on that message (an edit, `×N`); a notice raised while one is being shown is only logged, so a failing notice never loops. A window with no instance takes the same path.
- `ClaudeTopic.on_notice` holds notices for the next prompt's `[Bot notice(s)]` block (built in `_build_prompt`, after the `[Attached file(s)]` block); the same kind, what and error within a turn counts up (`×N`). An exception or a not-delivered notice is also submitted at once as its own prompt (`submit` queues it behind a running turn). After a notice prompt, further notices ride the user's next prompt (which reopens immediate ones), so a failure on a reply to a notice prompt never starts another. While the bot stops (`shutting_down`) a notice is only held: the held notices are saved with the window (`on_shutdown` and each notice during the stop) and replayed through `on_notice` when the window revives after the restart. `SESSION_BRIEF` says what each kind asks of Claude: resend, tell the user, no action.
- Every `except` in the package re-raises, raises a notice, or is normal control flow; `tests/test_except_handlers.py` walks the AST and fails on any other handler (only `notice_exception`, `on_notice`, `notice` and `show_notice` count as raising a notice; a log-only call does not), with an allowlist of caught types and of sites, each with its reason.

## Claude window: turn lifecycle & concurrency (`plugins/claude/driver.py`)

The most defect-prone area — message ordering and turn boundaries. The model below is essential; changes here need order-asserting MockBot tests.

Tasks and state:
- `_buffer_message()` (the window's text handler) buffers each inbound message and starts its downloads; `_flush_messages()` sends the window's buffer as one `submit()` (each message's context note and text in arrival order, then every saved file) once `MESSAGE_DEBOUNCE` passes with no new message and every download has finished — a forward and its comment, or an album, arrive as separate messages. A slash command skips the buffer.
- `submit()` runs in the message-handler task and holds `self.lock`. It queues an inbound prompt (`pending_writes`; mid-turn, its "queued ✓" ack is a send step) and writes it to the CLI stdin exactly as typed. The session note (`_session_note`: env tag, `SESSION_BRIEF` filled with the window's platform name and limits, app brief) is written to the window's file in the bot home (`session_notes/<window key>.md`, removed on close) and passed on each CLI spawn as `--append-system-prompt-file`, next to the workspace's `--system-prompt-file`, so every turn — a slash skill included — runs under it; a file, since one command-line argument is capped at 128 KiB.
- `_reader()` runs as its own task, draining the CLI stdout event stream; its `result` branch calls `_finalize_turn()`. It never sends: every message of the window goes out through `_send_in_order` — send steps, each its own task run after the ones queued before it — so screen order is queue order and the reader keeps reading while the platform is slow or flood-waited; a step still waiting on the one before it after `SEND_STEP_STALL` (60 s) logs a WARNING and keeps waiting. Every message a window posts or deletes goes through its `Topic.run_message_call` hook — the `Topic` send family (`send`, `send_rich`, `send_md`, `send_file`, `send_photo`, `delete`), a `Context` in that window, and the kernel's menus, prompts (`ask_buttons`, `menu`, `ask_text`, `pick_dir`) and help reply. The default runs the call at once; `ClaudeTopic` runs it as a send step (directly when already inside one), so command replies and menus (`/cancel`, `/kill`'s picker, an inline `/status`, `ctx.send`) are ordered the same way; a cancelled step releases its waiting caller. A prompt's tap future is registered before its message is sent, so a tap that comes the moment it shows is never lost; the prompt becomes the thread's active one (which a newer menu supersedes) only once it is on screen, and a prompt cancelled while its send is queued leaves nothing registered.
- A turn is opened by `_open_holder()` (every turn-entry path: submit, a background-completion turn, a prompt replay, the result fallback): fresh `TurnState`, `turn_open`, and the live card queued as a send step behind the previous turn's output, so the next turn's card opens only after the previous settle's last message is out. The reader's paths (a prompt replay, an `assistant` / `stream_event` with no turn open, the result fallback) go through `_open_next_turn()`: the oldest queued message's turn when one is queued (the CLI runs its input queue in order; a local slash command runs with no replay), else a turn of its own (a background completion). The card id lives on the turn (`turn.card_id`); `_heartbeat()` paints the open turn's card as frames, every `EDIT_INTERVAL`, and exits when the turn closes.
- Mid-turn messages: the CLI merges a prompt sent while a turn runs into that turn (one `result`) only at a tool boundary, echoing it as a prompt-replay `user` event before the `result`; the reader's fold path queues the delete of the "queued ✓" ack and a card move below it (`_reorder_holder`). A prompt sent with no tool boundary left (the model streaming its answer) is not merged: the CLI ends the turn, then runs the prompt as the next turn (its replay, or for a local slash command no replay, then its own `result`). That message stays queued with its ack on screen, the process is kept, and the next turn opens for it: its ack deleted, a fresh card at the bottom replying to the user's message.
- A process that exits with messages still queued (the reader's teardown) swaps each queued message's ack for a notice replying to it (`UNDELIVERED_NOTE`: not delivered, send it again); a cancelled reader (the window closing) posts none.

Turn boundary (the invariant that ordering hangs on):
- The `result` event IS the turn boundary, except a result whose `origin.kind` is `task-notification` (`is_notification_result`) while the prompt that opened the turn has not been replayed (`TurnState.awaits_replay`: set when a turn opens for a user prompt, from `submit` or a queued message, cleared by any prompt replay): the CLI ran a background-task notification first (on `--resume`, a task the previous process left unrecorded: `task_notification`, then an empty result with no model call), so the turn stays open for that prompt's replay and result. A message ack'd before it stays above this turn's finalized reply (folded into the turn when its replay came first, else run as the next turn); ack'd at/after it belongs to the next turn and stays below.
- `_finalize_turn()` takes `self.lock` so the boundary is atomic against `submit()`: it bumps `turn_seq`, keeps or drops `pending_writes` entries, closes the turn, and queues its settle (`_settle_turn`) as a send step.
- `turn_seq` (monotonic, bumped once per `result`) stamps each `pending_writes` entry at ack time. Finalize drops this turn's initiator (`<= boundary`) and keeps every queued message whose replay has not come, whatever its stamp; a kept one stamped `<= boundary` (ack'd during this turn, so below the card) makes the settle send message 1 below its ack instead of editing the card.
- No platform call happens under `self.lock`: `submit()` holds it across the CLI spawn and the stdin write only, `_finalize_turn()` and `_send_turn_note()` only queue send steps.

### Message-ordering invariant

The finalized reply is the BOTTOM-MOST of the turn's messages. Everything posted while the turn runs stays ABOVE it:
- the user's mid-turn messages (the turn folds their acks and moves the card below them; a mid-turn message whose replay has not come by the `result` is the next turn's, but stays above the finalized reply: the settle sends the output below its ack, and its own turn opens below that output),
- a command's mid-turn note (e.g. `/kill`'s "stopping…": queued under `self.lock`, then the card is re-sent below it), and
- the turn's timeline/events.

A message ack'd at/after the boundary is the next turn's and stays below the finalized reply.

The background-jobs panel is not a turn message: it sits below everything, the finalized reply included. It is a bottom frame (`show_bottom_frame`): the kernel records the newest message id per thread (every essential call's result, every inbound message, and a landed topic rename, whose service message the bot never receives), and any id newer than the panel's schedules one silent move of the panel below it — the old copy's delete (or, when it can't be deleted, a stub edit) and the new send as one paired step (Frame-skip output → Bottom frames), the send retried until it lands, so at most one panel is on screen. This runs in the frame task, independent of the heartbeat, the between-turn updater, or the CLI process; one INFO log line per re-anchor (with its gap: delete issued → send landed) and per dropped attempt.

### Finalized-turn format

At settle, a turn renders as new messages in this order, each piece waiting out flood-waits and retried until it lands (no gap, no skip); a network error or 5xx gets the bounded retries above:
- the tool-call part: one or more messages (`ui.expandable_pages` → `ui.Pages`, laid out by the window's adapter; Slack posts the summary line, then each page as a reply in its thread); the first is the summary line `🔧 N · 💬 N · duration · ↓ tokens · ctx P% (T) · 5h P% · 7d P%` as plain text with a collapsed expandable block under it, each later one a collapsed expandable block headed `↳ i/n`; timeline entries are packed into as few messages as fit; nothing is cut — an entry longer than a message is split across messages; a turn with no timeline still gets the summary line alone, with no block;
- the answer part: one or more messages (standard Markdown rendered by the adapter, split to fit); an empty answer is `(no reply)`; the suggestion buttons ride the last answer message;
- the `[[attach]]` files.

Rules:
- The live card always becomes tool-call message 1 (a `land_frame` edit); if that edit fails, the card is deleted and message 1 sent fresh — the live working frame never stays as a finalized card.
- No caps: no tool-detail cut, no answer-message cap.
- The live card while the turn runs shows the tail only, under the status line `✶ Word… 12s · ↓ 1.2k · ctx 21% (42.4k) · 5h 3% · 7d 0%` (↓ = output tokens).
- Context tokens = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` of the main agent's last `message_start`. The context window comes from `result.modelUsage[<model>].contextWindow`, saved per window (before the first result: 1M for a model id ending `[1m]`, else 200k; a model switch clears it). Quota is the newest `rate_limit_event`'s `unifiedWindows`, kept per account (config dir) on the plugin, so every window on that account shows it; ⚠️ leads the quota part when `status` is not `allowed`. There are no separate quota alert messages.

## Background jobs (`plugins/claude/background.py`)

- A job is registered from its launch result — a background Bash or an Agent launch (`backgroundTaskId` + its `tasks/<id>.output` path). It ends when a completion event names it, when a Read of its output file finds the exit marker, or when a probe reads the exit marker the CLI appends to the output file (`[exited with code N]`, `[killed]`); with no marker, a job past its grace whose file nothing holds open ends as ◼.
- The panel is its own message, placed per the message-ordering invariant. It lists running jobs, plus each finished job's ✓ / ✗ / ◼ for `FINISHED_LINGER` seconds. The updater (`_background_updater`) only ticks its clock and prunes, while it shows rows — started when a job registers or a settle leaves rows, never stopped by a turn or the CLI process ending.
- `/kill <job>` stops a job through the CLI that owns it: a `stop_task` control request, which kills the job's whole process tree. With no live CLI, `kill_file_holders` (kernel) kills the processes holding the output file, every process in a session whose leader is one of them (the job's shell; a reader in another terminal brings only itself), and all their descendants, and refuses a set that reaches the bot's own group or session. Its mid-turn note follows the message-ordering invariant.

## Mid-session config switching

Two scopes:
- Per-window (per topic): model, effort, account, workspace. Stored on the topic, saved per window.
- App-wide (the plugin): permission mode; and the pools — the model list and workspace roots.

Uniform switch mechanism: set the value, then kill an idle proc so the next message respawns with it (an in-flight turn is untouched). `/clear` and a workspace switch (a fresh session) drop it the same way. Every switch menu shows the current value with a ✓. `/model` reset restores the app's `Claude(models=[…])` list.

Pool editing (add/remove/reset) belongs only where the pool is user-editable (model list, workspace roots). Fixed sets (permission mode, effort) are switch-only.

Command naming is singular — each command's primary act is selecting the active value for the session: `/account`, `/mode`, `/model`, `/effort`, `/workspace`. The typed forms (`/model add|rm|reset`, `/workspace add|rm`) keep working from the keyboard.
